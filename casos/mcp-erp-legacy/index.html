Recuperar el conocimiento de un ERP legacy con servidores MCP

Stack

  • Python
  • MCP (SDK oficial)
  • python-oracledb
  • Oracle 19c
  • JD Edwards EnterpriseOne 9.2
  • JD Edwards AIS / Orchestrator
  • Agentes de IA

Contexto

Una empresa de servicios industriales opera su negocio sobre JD Edwards EnterpriseOne 9.2 con base Oracle 19c. El responsable de aplicaciones se fue y el conocimiento del sistema se fue con él: orquestaciones, seguridad, macros que escriben en producción y tareas programadas, todo sin documentar. El objetivo: saber qué depende de qué, cerrar riesgos y poder operar.

Solución

Construí dos servidores MCP en Python que le dan a un agente de IA (cliente MCP) acceso de solo lectura al ERP:

  • Servidor de base de datos (Oracle): query (solo SELECT/WITH, resultado tabular con límite de filas), describe_table (columnas y comentarios) y udo_xml (definiciones de orquestaciones, reglas, notificaciones y schedules del Orchestrator, con secretos ocultos).
  • Servidor AIS (API REST de JD Edwards): configuración, orquestaciones disponibles, estado del programador y lectura de tablas con límite de filas. Lista cerrada de endpoints; no puede ejecutar ni detener nada.

El agente investiga y redacta; yo valido, decido y envío. Un subagente lector consulta la documentación ya generada para no repetir trabajo.

Arquitectura

Decisiones de diseño

  • Solo lectura en tres capas: validación de la sentencia (una sola, solo lectura, sin FOR UPDATE ni paquetes peligrosos), transacción READ ONLY con ROLLBACK y cuenta dedicada para el agente.
  • Límites: máximo de filas por consulta y timeout de 120 s.
  • Auditoría: cada consulta queda registrada (sentencia, filas, duración) sin guardar los datos.
  • Secretos: credenciales en el gestor de credenciales del sistema operativo; contraseñas y tokens se ocultan antes de llegar al modelo.
  • Humano en el circuito: el agente nunca escribe en producción.

Resultados

  • 14 de 14 orquestaciones productivas documentadas, incluido el circuito crítico de facturas.
  • 692 roles catalogados y 918 usuarios habilitados auditados; 885 usuarios detectados con un conflicto de roles en un programa de compras.
  • 355 usuarios con visibilidad sobre todas las unidades de negocio identificados como riesgo.
  • 3.365 archivos de Excel/VBA analizados y 89 macros inventariadas, 20 de ellas escriben en producción.
  • 13 consultas SQL reutilizables y entregables formales para el área de Seguridad.
  • Relevamiento principal en tres semanas; 52 commits en dos meses.

Próximos pasos

Tests automáticos de las guardas de solo lectura, permisos de base más acotados y versión open source genérica.
