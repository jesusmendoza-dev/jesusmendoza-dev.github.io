Recovering a legacy ERP's knowledge with MCP servers

Stack

  • Python
  • MCP (official SDK)
  • python-oracledb
  • Oracle 19c
  • JD Edwards EnterpriseOne 9.2
  • JD Edwards AIS / Orchestrator
  • AI agents

Context

An industrial services company runs on JD Edwards EnterpriseOne 9.2 over Oracle 19c. When the applications lead left, the system's knowledge left with him: orchestrations, security, macros writing to production and scheduled jobs, all undocumented. Goal: know what depends on what, close risks and be able to operate.

Solution

I built two Python MCP servers that give an AI agent (MCP client) read-only access to the ERP:

  • Database server (Oracle): query (SELECT/WITH only, row-limited), describe_table, and udo_xml (Orchestrator definitions with secrets redacted).
  • AIS server (JD Edwards REST API): configuration, available orchestrations, scheduler status and row-limited table reads. Closed endpoint allow-list; it cannot run or stop anything.

The agent investigates and drafts; I validate, decide and send.

Architecture

Design decisions

Read-only in three layers (statement validation, READ ONLY transaction + rollback, dedicated account); row limits and timeouts; audit log without data; OS credential store and secret masking; human in the loop, no production writes.

Results

14/14 production orchestrations documented · 692 roles catalogued · 918 enabled users audited · 885 users with a role conflict found · 3,365 Excel/VBA files analyzed, 89 macros inventoried (20 write to production) · 13 reusable SQL checks · formal deliverables for Security · core discovery in three weeks.
